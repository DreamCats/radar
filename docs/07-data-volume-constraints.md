# 07 · 数据量级约束与原数据看板设计

> 关键工程约束。影响存储 / API / 前端渲染整条链路。
> 记录日期：2026-06-03

## 实测量级

单日真实消息量（基于 `~/.config/stock-news/data` raw 数据）：

| 日期 | 个人群 | 个人消息 | 合计 |
|---|---|---|---|
| 2026-04-15 | 2032 | 894 | **2926** |
| 2026-05-10 | 1818 | 767 | **2585** |

- **单日 2600~3000 条**，本人估计 3000+ 成立。
- 历史累积：几十万~百万级。

## 由此确定的设计决策

### 1. 前端：绝不一次性渲染全量
- **虚拟滚动**：只渲染视口内 ~30 行（用 `@tanstack/react-virtual`）。
- **后端游标分页**：API 按 `cursor`（message_time / message_id）分页，滚到底再拉。

### 2. 主视图形态：A 的筛选 + B 的列表详情（融合）✅
本人决策：
- 保留 **A 方案顶部那排筛选器**（来源 个人群/个人消息、时间段、群白名单导航），
  让用户**先缩小范围**，而不是一上来面对 3000 条。
- 采用 **B 方案的「列表 + 右侧详情」布局**：点任意消息看 message_id / 机构 / 识别个股。
- 列表用虚拟滚动兜底全量。

> 核心理念：3000 条人看不完也不该看完。先靠「过滤器缩范围」，再靠虚拟滚动兜底。

### 3. 降噪力度：群白名单 + 搜索筛选（硬过滤，不碰 LLM）✅
本人决策——阶段一只做「硬」降噪：
- 群白名单：过滤生活群 / 作业群等非投研群（入库前或查询时）
- message_id 去重
- 关键词 / 群 / 时间 / 来源 多维筛选
- **不引入 LLM**（LLM 分类留到阶段二信号雷达）
- 与「先简后繁」初衷一致

### 4. 存储：SQLite + 索引 + FTS5
- 几十万行对 SQLite 是小 case，但查询要快需建索引：
  - `message_time`（时间范围筛）
  - `group_name`（按群筛）
  - `message_id` UNIQUE（去重主键）
- 全文搜索用 SQLite **FTS5**（搜内容）

## 对 demo 的影响
- 新增融合版 `01f-filtered-detail.html`：A 筛选器 + B 列表详情 + 虚拟滚动占位提示。
- 这是阶段一原数据看板的**主推布局**。
