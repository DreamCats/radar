# 个股证据链生命周期策略

## 一句话

这个策略不再让本地规则直接判断“叙事阶段”。

它的核心是：

```text
本地计算负责发现股票和整理证据链；
LLM 负责基于证据链讲清投资逻辑、判断阶段、给出可解释标签。
```

投资人每天不应该一条条盯 5000 条消息，也不应该靠群里刷屏才知道一个股票。系统要先从当天新增消息里找出“可能值得关注的股票”，再把这个股票最近 40 天的原始消息证据整理出来，交给 LLM 判断它现在处在什么阶段。

## 背景

之前的“叙事生命周期”尝试把 anchor、叙事、股票绑定和阶段快照都本地算出来。

这个方向暴露了一个关键问题：叙事是逻辑，不只是共现。比如一个词在错误语境里被命中，本地规则可能把无关股票绑定到错误主题上，后面再怎么算分都会越来越脏。

更合理的边界是：

- 本地计算做高召回、可追溯、可去重的证据检索。
- LLM 做证据阅读、逻辑归纳、阶段判断。
- 每一个阶段标签都必须能反查到原始消息证据。

## 解决的问题

这个策略解决的是个人投资者每天打开 radar 时的三个问题：

1. 今天新增消息里，哪些股票值得进入候选池？
2. 这只股票过去一段时间到底积累了什么证据链？
3. 现在看到它时，是早期线索、逻辑成型、正在扩散，还是已经拥挤？

它不直接解决：

- 买卖建议。
- 仓位。
- 止损止盈。
- 财务估值完整分析。
- 消息真假最终验证。

## 总体流程

默认运行时间是投资人当天打开工作台时。

输入窗口默认是：

```text
昨日收盘后 -> 当前时刻
```

如果系统已经有处理水位，也可以用：

```text
上次处理成功时间 -> 当前时刻
```

主流程：

```text
新增消息窗口
  -> 降噪、过滤、去重
  -> 识别明确股票
  -> 生成股票候选
  -> 查询该股票最近 40 天历史消息
  -> 整理证据链
  -> 补行情和成交额
  -> 构造 LLM 证据包
  -> LLM 判断阶段和标签
  -> 保存判断版本、当前状态、证据引用
```

这里的股票只是入口，不是结论。看到“顺络电子”这几个字，只说明它需要被倒查，不说明它一定有机会。

## 第一步：新增消息降噪

原始新增消息可能有 500 条，但不应该全部进入后续流程。

先做本地降噪：

- 保留 `research`（研究）、`event`（事件）、`recommendation`（推荐）、`industry`（行业）等高价值分类。
- 默认降低 `chat`（闲聊）和 `unknown`（未知）的权重，但如果里面出现明确股票和强逻辑词，可以保留。
- 过滤低价值群、重复转发、纯表情、无内容短句。
- 对相同内容做指纹去重。
- 对同一个人把同一段内容转发到多个群的情况，只保留一条主证据，同时记录转发范围。

去重不能只删掉重复消息，还要保留这些信息：

- 第一次出现时间。
- 转发了几个群。
- 有几个不同发送人。
- 是否只是同一份内容复制扩散。

因为“独立来源重复”和“同一段内容到处转发”含义完全不同。

## 第二步：识别当天候选股票

从降噪后的消息里识别股票。

第一版以 Tushare 股票名称和代码为主：

- 股票全称。
- 常用简称。
- `ts_code`。
- 必要时补充本地别名。

这里要比旧 anchor 更严格。股票识别的目标是“明确股票”，不是概念词共现。

需要避免这些问题：

- 不能把行业词误当股票。
- 不能把词的一部分误匹配成股票。
- 不能因为股票和概念出现在同一条消息里，就直接认为它们存在投资逻辑绑定。

当天消息里命中的股票，会进入候选池。候选池只代表“需要倒查”，不是“值得买”。

## 候选召回：双通道

第一版不能只靠一个阈值。

只用 `去重触发 >= 7`，成本可控，但会漏掉扩散初段；只用 `去重触发 >= 3`，召回很高，但弱证据和列表噪声太多。

所以采用双通道召回，最后按 `ts_code` 合并去重：

```text
通道 A：热度通道
去重触发 >= 7

通道 B：早期强证据通道
去重触发 >= 3
AND 发送人 >= 2
AND 会话 >= 2
AND 强证据达标
```

同一只股票可能同时命中两个通道，只保留一条候选，但记录命中来源。

强证据不是简单关键词命中。第一版要求强词出现在股票名、代码附近，避免整条长消息里别处出现“涨价/调研”就误判。

强证据分层：

| 类型 | 例子 | 权重 |
| --- | --- | ---: |
| 产业催化 | 涨价、缺货、订单、锁单、排产、量产、验证、中标、业绩上修 | 3 |
| 公司/机构动作 | 董秘、IR、反路演、1v1、一对一、调研、电话会议 | 3 |
| 研究覆盖 | 深度报告、首次覆盖、点评、更新、纪要、测算、专家会 | 2 |
| 明确推票 | 强推、重点推荐、继续推荐、首推、金股、call | 2 |
| 行情确认 | 涨停、放量、成交额、大涨、异动 | 1 |

早期强证据通道的第一版规则：

```text
去重触发 >= 3
AND 发送人 >= 2
AND 会话 >= 2
AND (命中产业催化 OR 强证据分 >= 8)
```

这不是最终投资结论，只是“值得倒查 40 天证据链”的入口。

## 第三步：查询最近 40 天历史证据

对每个候选股票，查询最近 40 天相关原始消息。

窗口规则：

```text
evidence_start = as_of_time - 40 天
evidence_end = as_of_time
```

为什么是 40 天：

- 太短会看不到从早期线索到扩散的过程。
- 太长会把旧逻辑、旧行情和过期研究混进来。
- A 股很多主题从线索到拥挤通常发生在几周内，40 天足够覆盖一轮主要扩散链。
- 成本可控，适合每天增量跑。

如果本地数据不足 40 天，需要显式标记：

```text
历史覆盖不足，只能做冷启动判断。
```

历史检索不只看当天新增消息，而是要把这个股票最近 40 天所有相关消息按时间线拉出来。

每条证据至少保留：

- `message_id`。
- 时间。
- 发送人。
- 群或会话。
- 消息分类。
- 原文摘要或原文片段。
- 命中的股票名称或代码。
- 内容指纹。

## 第四步：证据分层

不是所有消息都同等重要。

本地先把历史消息整理成证据项，给 LLM 读的时候降低噪音。

建议证据类型：

| 类型 | 含义 | 例子 |
| --- | --- | --- |
| 调研/交流 | 公司、董秘、专家、产业链交流 | 约董秘、专家会、产业反馈 |
| 报告/更新 | 卖方正式更新逻辑 | 公司点评、行业更新、业绩点评 |
| 路演/推票 | 明确面向机构分发 | 路演预告、反路演、1v1、晨会 |
| 推荐/call | 明确建议关注或强推 | 继续推荐、重点关注、强 call |
| 行业逻辑 | 股票被放进行业变化里 | 涨价、缺货、国产替代、AI 服务器 |
| 行情确认 | 价格和成交额开始反应 | 放量上涨、涨停、回调承接 |
| 群聊扩散 | 大量群开始讨论 | 多群转发、问还能不能买 |
| 风险/反证 | 逻辑可能被削弱 | 澄清、订单不及预期、价格回落 |

证据分层的目标不是给结论，而是让 LLM 看到一条干净的时间线。

## 第五步：构造 LLM 证据包

不能把 40 天所有原文无脑塞给 LLM。

本地需要构造一个证据包。

建议结构：

```text
股票基础信息
  - 股票名
  - ts_code
  - as_of_time
  - 证据窗口

上一版状态
  - 如果之前判断过，放上一版阶段、理由和关键证据摘要

新增触发
  - 今天为什么被重新捞出来
  - 新增了哪些消息

历史证据时间线
  - 最早线索
  - 逻辑成型证据
  - 多来源扩散证据
  - 路演/推票证据
  - 行情确认
  - 群聊扩散
  - 风险或反证

去重说明
  - 哪些内容是重复转发
  - 哪些是独立来源

行情摘要
  - 近 5/10/20 日涨跌幅
  - 成交额变化
  - 是否已经明显异动
```

证据包大小要受控。

建议第一版限制：

- 最多 60 条证据项。
- 优先保留时间线上的阶段变化点。
- 重复内容只放代表消息。
- 最新新增消息必须保留。
- 风险和反证不能丢。

## 第六步：LLM 输出什么

LLM 不直接输出买卖建议。

它输出结构化判断。

建议输出字段：

```text
stock_name              股票名
ts_code                 股票代码
as_of_time              判断时间
stage                   当前阶段
confidence              置信度
stage_reason            为什么是这个阶段
key_logic               当前市场在讲什么逻辑
evidence_chain          支撑这个判断的证据链
incremental_change      相比上一版有什么增量
pricing_view            股价是否已经明显定价
crowding_risk           是否拥挤
open_questions          下一步需要验证的问题
decision_note           给投资人的阅读提示，不是买卖建议
```

阶段建议仍然保留 6 类，但必须让 LLM 基于证据判断：

| 阶段 | 中文含义 | 证据表现 |
| --- | --- | --- |
| `lead` | 线索期 | 少数高质量线索出现，扩散很弱 |
| `seed` | 种子期 | 调研、专家、产业反馈开始验证 |
| `formed` | 论证期 | 报告、点评、测算框架把逻辑讲清楚 |
| `spreading` | 扩散期 | 多来源重复同一逻辑，传播范围扩大 |
| `pricing` | 定价期 | 股价和成交额开始明显响应 |
| `crowded` | 拥挤期 | 群里刷屏、路演密集、价格已大幅反应 |

LLM 必须给出每个阶段判断对应的证据引用。

不能只说：

```text
顺络电子处于扩散期。
```

应该说：

```text
顺络电子处于扩散期，因为 5/27 后多个来源开始围绕 AI 电感、MLCC 缺货、涨价逻辑重复推荐；
6/5 多家卖方集中更新，6/8 出现路演和反路演证据；
同时股价和成交额已经明显响应。
```

## 第七步：状态更新

股票状态不能只存一个最终标签。

要存每一次判断版本。

一只股票可能经历：

```text
2026-04-29  进入候选池
2026-05-27  逻辑增强
2026-06-05  发酵确认
2026-06-08  推票扩散
2026-06-09  拥挤风险上升
```

每一次判断都要记录：

- 当时的 `as_of_time`。
- 使用了哪个证据包。
- LLM 输出的阶段。
- 关键理由。
- 新增证据。
- 是否更新当前状态。

当前状态只是最新视图，不是历史真相。

历史判断不能覆盖，要追加。

## 增量判断规则

如果一只股票之前已经判断过，不能每次都重新从零判断。

流程应该是：

```text
读取上一版状态
  -> 找 last_judgement_time 之后的新证据
  -> 判断是否有实质增量
  -> 有增量才调用 LLM
  -> LLM 决定维持、升级、降级、转拥挤或标记过期
```

什么叫实质增量：

- 新出现高质量来源。
- 新增报告、路演、调研、专家会。
- 同一逻辑从一个来源扩散到多个来源。
- 逻辑从“提到股票”变成“明确原因”。
- 行情出现明显放量或涨跌。
- 出现风险或反证。

什么不算实质增量：

- 同一段内容复制到多个群。
- 单纯喊涨。
- 只有股票名，没有逻辑。
- 只有闲聊，没有新增事实。

## 当前落地数据产物

第一版不继续复用旧的叙事快照表。

当前后端先落三张表：

| 表 | 作用 |
| --- | --- |
| `stock_message_mentions` | 消息-股票命中索引，解决 40 天回捞不能反复 `LIKE` 扫全库 |
| `stock_lifecycle_candidates` | 某个 `as_of_time` 下的候选池、触发统计、召回通道 |
| `stock_lifecycle_judgements` | LLM 阶段判断，追加写，保留证据引用 |

表之间的核心关系：

```text
stock_message_mentions
  -> stock_lifecycle_candidates
  -> stock_lifecycle_judgements
```

每个阶段标签必须能追到：

```text
stage -> judgement -> evidence_pack -> message_id -> 原始消息
```

这条链断了，标签就不可信。

后续如果 UI 需要更快读取当前状态，再补 `stock_lifecycle_state`。第一阶段先不加，避免过早维护一张派生状态表。

## 耗时和默认参数

当前默认参数：

```text
新增窗口：as_of 前一日 15:00 -> as_of
历史证据窗口：40 天
召回：热度通道 + 早期强证据通道
候选上限：120 只
LLM：默认关闭；需要时用并发池开启
```

粗估耗时：

| 阶段 | 优化后目标 |
| --- | ---: |
| 读取四类消息 + 股票匹配 | 1-3 秒/天 |
| 建立 `stock_message_mentions` | 首次 40 天较慢，之后增量秒级到十几秒 |
| 候选合并排序 | 1 秒内 |
| 40 天证据回捞 | 1-6 秒/天 |
| LLM 16 并发 | 约 3-6 分钟/天 |
| LLM 32 并发 | 约 2-4 分钟/天 |

历史回放时，`去重触发 >= 3` 会产生更多候选。5/1-6/9 的实测口径里，严格强证据通道约 6328 个 stock-day，日均 158 只。第一版不应全量送 LLM，而是合并去重后按强证据分、发送人、会话、热度排序，送前 80-120 只。

## 和旧方案的区别

旧方案：

```text
anchor 共现
  -> narrative 归并
  -> 本地规则判断阶段
  -> 股票绑定
  -> 快照
```

新方案：

```text
当天股票触发
  -> 最近 40 天原始证据链
  -> LLM 读证据讲逻辑
  -> 阶段标签带证据版本
```

旧方案的问题是本地规则太早做了语义判断。

新方案把本地计算降级成证据工程，把语义判断交给 LLM，同时要求 LLM 的每个结论都引用证据。

## UI 应该怎么呈现

WebUI 暂不在当前阶段实现。后续做策略页时，投资人打开策略页，不应该先看到一堆分数。

应该看到候选股票卡片：

```text
顺络电子
阶段：扩散期 / 定价期
触发原因：今日新增路演和反路演消息
核心逻辑：AI 电感、TLVR、涨价、客户验证
证据链：4/29 公司点评 -> 5/27 多来源强化 -> 6/5 卖方集中推荐 -> 6/8 路演扩散
风险：股价已明显上涨，拥挤风险上升
```

点进去后展示：

- 时间线。
- 原始消息证据。
- LLM 阶段判断。
- 上一版判断和本次增量。
- 行情确认。
- 风险或反证。

这比直接展示“早期分数 82”更容易让投资人理解。

## 第一版实现边界

第一版只做个股证据链，不做复杂主题图谱。

当前分三步：

1. **后端/CLI 证据链**
   - 建 `stock_message_mentions` 索引。
   - 从当天新增窗口生成候选池。
   - 回捞最近 40 天证据。
   - 默认不调用 LLM。

2. **LLM 判断版本**
   - 把证据包送 LLM。
   - 输出结构化阶段判断。
   - 保存判断和证据引用。

3. **策略页展示，下阶段**
   - 展示候选股票。
   - 展示证据链。
   - 展示阶段和原因。
   - 支持查看历史判断版本。

暂时不做：

- 全市场主题图谱。
- 复杂概念归并。
- 基于 anchor 共现的叙事合并。
- 自动交易。

## 废弃表清理

上一版叙事生命周期表不再作为优先实现方向。

可清理候选：

```text
normalized_anchors
narratives
narrative_snapshots
narrative_stocks
narrative_stock_snapshots
```

清理必须显式执行，不跟随普通启动自动删除：

```bash
radar strategy cleanup-deprecated --confirm
```

`message_anchors`、`aggregate_refine_results`、`recommendation_events`、`recommendation_backtest_windows` 暂时不自动删除。它们仍可能被旧策略、榜单、回测或诊断页面引用，后续确认无依赖后再清。

## 验收标准

拿顺络电子这种案例验收。

系统应该能回答：

- 它第一次进入候选池是什么时候？
- 当时依据是什么原始消息？
- 5/27 为什么应该升级？
- 6/5 为什么已经不是早期？
- 6/8 路演和反路演为什么代表扩散或拥挤？
- 每个判断能不能点回原始消息？

如果系统只能输出一个阶段，但解释不出证据链，就不合格。

如果系统能像人工复盘一样讲清：

```text
哪个时间点，谁说了什么，逻辑如何增强，价格如何响应，所以阶段如何变化
```

这个模型才算成立。
